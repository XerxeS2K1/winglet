# Winglet v0.12.10

A security release. Three problems found by a code scan of Winglet are fixed. None has been seen exploited, and none was tried against a real attack; each fix has its own tests.

## A crafted image link could send your sign-in token to another host

The app attached your device token to image and file links that start with a path on your server. A link like `//other-host/x` or `@other-host/x` could point somewhere else and take the token with it. The app now loads a path only if it stays on your server, and loads nothing otherwise.

## Pairing over plain http

Pairing over an address that isn't encrypted let anyone on the network path read the pairing code and impersonate the server. Pairing and moving a server now refuse a plain http address unless it is on your own network, loopback or Tailscale. An address typed without a scheme now defaults to https, except for those local addresses. Servers you have already paired keep working.

If pairing refuses an address you expected to work, use its https address, or its Tailscale address.

## Regenerate skipped the command checks

Regenerating a reply sent the stored prompt back to Hermes without the checks a normal message gets. A device token alone could regenerate a command meant to need the app's signed request (such as turning approvals off), and a member could regenerate an owner-only command. Regenerate now applies the same checks before it rewinds anything. A signed-only command is never re-sent from regenerate: send it again from the app.

## Not covered

The scan reported ten more findings: one high (dependencies with known vulnerabilities), one medium (release workflow actions pinned by movable tags) and eight low. They are not fixed in this release. The changes are not tested on a phone yet. The app and the server plugin update together through the in-app Update.
